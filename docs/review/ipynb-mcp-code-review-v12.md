## 三、本轮新发现

【V12-1】
严重程度：🔴 阻塞（**本轮新引入的回归：下溢到零的字面量被静默改写成 `0`——盘上也丢字节**）
所在位置：`src/core/json-exact.ts:161-174`（`losesInformation`）· 根因是 **`:166` 的早退 `if (value === 0) return isNegativeZero(literal);`** · 文案在 `src/core/outputs.ts`
问题描述：**合法 JSON、nbformat 判 VALID** 的字面量 `1e-400`（以及 `1e-330`/`1e-324`/`2e-400`）在 read 方向被交付成 `0`、**零警告**，并且在**编辑一个无关 cell** 之后**从盘上消失（变成 `0`）**。而 v10 的旧判据下这些字面量是**逐字节保留**的（子代理用 `8384931` 的旧 `json-exact.ts` 编译后直跑对照：`old=true → cur=false`），所以我 v11 报告里实测过的"`1e-400` 保留"是在本轮被改坏的——**这是本轮修复引入的回归**。
详细分析（**主审实测**，`application/json` 放一个字面量 + 编辑无关 cell）：
```
1e-400    losesPrecision=false  交付=0  警告=0   编辑无关 cell 后盘上 = 0        ✗ 字节丢失
1e-330    losesPrecision=false  交付=0  警告=0   盘上 = 0                        ✗
1e-324    losesPrecision=false  交付=0  警告=0   盘上 = 0                        ✗
2e-400    losesPrecision=false  交付=0  警告=0   盘上 = 0                        ✗
-1e-400   losesPrecision=true   交付=0  警告=1   盘上 = -1e-400（保留）           ⚠ 行为相反 + 文案假
         警告原文："json value -1e-400 is negative zero; the value is exact but its sign is not carried by a
                   JSON response, so a client reads it as 0"
对照：1e400（上溢）交付 null + 警告 "outside the range … delivered as null"    ✓ 有警告
      1e-320（次正规）交付 1e-320、盘上保留                               ✓
```
三个问题叠在一起：① **正的**下溢**静默丢字节**（本产品的第一条卖点）；② **负的**下溢反而保住了字节，却拿到一句**两处为假**的警告（它不是负零，值也不再 "exact"）——**行为与文案都是反的**；③ 与上溢的孪生兄弟**不对称**（上溢告知、下溢不告知），违反 D-056 自述的不变式①（"值变了必须警告"）。
触发面（如实）：需要**手写或第三方工具写出**的字面量——kernel 产不出（Python 自己把 `1e-400` 求值成 `0.0`，我实测 run 路径此时无缺陷）。但一旦存在，它是**静默的、落在盘上的**，且由一个**无关编辑**触发——与 v10-3 的形态、级别相同。
**量级与"守卫为什么看不见"（子代理实测，我采信并认为关键）**：`1e-324`…`1e-400` 共 **77 个十进制指数**落入此洞（另采样 2000 个 `{1,2,5,9,9.9}e-N` 形态，382 个命中）；`5e-324`（最小次正规）不受影响。**现有守卫在这一点上与被测判据同构**——`tests/unit/json-number-forms.test.ts:407-412` 对 `warned:false` 的形态断言 `String(parsed) === String(Number(literal))`，而对 `1e-400` **两边都是 `'0'`**，所以**把它加进表里也会绿**；`FORMS` 表里最近的下溢样本是 `1e-300`。⇒ 修复时必须同时换掉那条断言的判据（例如断言"盘上逐字节保留"而不是"两条规范化结果相等"）。
修复建议：删掉 `:166` 的 `value === 0` 早退，只保留 `isNegativeZero` 特例，并把"下溢到零"单列：子代理给出的判据 `if (value === 0) return isNegativeZero(literal) || /[1-9]/.test(literal);` 已实测判别力（24 个样本里只翻转下溢那几个；注意 `0e-5` 这类"有效数字全零"的字面量不应被误标）。把 `1e-400`/`1e-324`/`1e-330`/`-1e-400` 加进 `FORMS`（`warned: true`）与 `valueChanges`；`-1e-400` 的文案要**单独写**（"underflows to zero; the sign is lost"），不能复用负零那句。
设计文档对齐：SPEC §6 R2「不静默改坏」、§5.5.7（**注意**：§5.5.7 许可的是"规范化"；`10⁻⁴⁰⁰ → 0` 是**逻辑变化**，不在其列）、D-056 不变式①②。

【V12-6】
严重程度：🟢 建议（**产品层面的知情项：值等价的"写法规范化"覆盖 16/28 种字面量**）
所在位置：SPEC §5.5.7（第 694 行）· `README.md:89` · D-056 的"代价（刻意接受）"
问题描述：本轮把判据改成"按值"之后，**值相等、只是写法不同**的字面量不再打 marker，于是**未修改区域**会在一次无关编辑后被规范化。我实测 28 种字面量里 **16 种被改写**：
```
100.0→100  1e2→100  1E+2→100  1.0e2→100  1e+02→100  1.5e3→1500
0.10→0.1   1e0→1    1.0→1     1.00→1     0.0→0       0e0→0
2.0→2      1e-05→0.00001     1e21→1e+21   1e-400→0
（保留：-0 / -0.0 / 0.00001 / 1e-320 / 2**64 / 1.0000000000000001 / 0.1234…345 / 1e400 / 0.1 / 123.456 …）
```
**这不是缺陷**：SPEC §5.5.7 明确写着"`JSON.parse → 修改 → JSON.stringify` 会把 `\uXXXX` 转义、**指数形式数字等规范化**，因此**未修改区域也可能出现整文件级 diff**；本插件的承诺是'**逻辑不变**'，不是'字节最小 diff'"，且 `README.md:89` 已如实声明，D-056 也把这个代价登记为刻意接受 ✓。我把它列出来只是**知会决策者**：从这一轮起，"不会静默改坏"的实际含义是"**不会静默改变数值**"，而不是"不会改动字节"；Python `json.dumps` 的常见输出（`2.0`/`100.0`/`1e-05`）都会在无关编辑中被规范化。
**一个可选建议**（不影响本轮结论）：两个目标其实**不冲突**——"保留原文"由 marker 决定，"是否警告"由值是否变化决定，**可以静默保留**（打 marker 但不发警告）。那既满足 v10-3 的字节保真，也满足 v11-1 的"不误报"。是否这么做取决于是否愿意接受"未修改区域出现整文件 diff"（SPEC 允许，但不要求）。

**本轮没有发现**：整机不可用 / 协议错误 / 键丢失 / 图片伪造。**但有**：一处**静默改写盘上字节**（V12-1，下溢到零，本轮新引入的回归）、一处**归因丢失且零覆盖**（V12-3，run 路径图片警告按 code 去重）、**三行"已修"没有对应产物**（V12-4，虚报族复发；且新门禁抓不到其中两行），以及五处文档/注释小账（V12-5）。
