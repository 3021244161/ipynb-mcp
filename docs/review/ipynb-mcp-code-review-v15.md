### 2.2 F3（字节估算低估）→ ✅ **真修**（代价是"整项丢弃"而非"截断"）

```
v14: 3 MiB 反斜杠 → ✗ Connection closed            v15: ✓ 472 ms，0.00 MiB，warnings=1

```
非 ASCII 与转义富集内容不再打死客户端 ✓。注意交付形态从"截断"变成"**整项丢弃**"（响应 0.00 MiB + 1 条警告）：安全，但模型拿到的是"这一项没了"而不是"截短的一段"。是否可接受取决于文案是否说清（见 §三 V15-2）。

### 2.3 F1（截断循环不收敛 → 挂死）→ ⚠️ **挂死已修，但同一形状仍会断连客户端**（新发现，🔴 级）

**挂死确实没了**：同一夹具从"30 000 ms 无响应"变成 **1028 ms 返回** ✓ —— 循环终止了（F1 的核心修复到位）。

**但客户端仍然会死**，而且触发面很清楚（**尺寸边界对照**，同一夹具只改源码大小）：

| 源码 | 响应 | 结果 |
|---|---|---|
| 3 MiB | **6.00 MiB** | ✓ 正常、warnings=0 |
| 5 MiB | ≈10 MiB | ✗ **`McpError -32000: Connection closed`** |
| 7 MiB | >10 MiB | ✗ 断连 |
| 12 MiB（v14 的 F1 夹具） | >10 MiB | ✗ 断连（1028 ms 返回，不再挂死） |

**根因**：预算**对 `cells[].source` / `source_preview` 没有杠杆**——`TEXT_FIELDS` 只含 `text`/`value`/`html`，丢弃阶段又（按 F4 的修复方向）不再删 cell。于是"载荷主体是源码"的 `include_source='full'` 响应**绕过整个预算**，帧超 10 MiB 就被 SDK 掐断：客户端看到 `-32000 Connection closed`、无错误码、该 server 名下所有 kernel 一起死——**正是 V13-1 要消灭的形态**。另注意响应 ≈ **2×** 源码（同一份文本在载荷里出现两次），所以 5 MiB 源码就会越线。

**触发面**：`include_source='full'` + 源码 ≥ ~5 MiB（或 `preview` + 单行超长）。真实 notebook 里 5 MiB 源码不常见，但**大 notebook + 大 cell（内嵌数据/长文本）**会命中，且这正是本轮旗舰场景（"37.5 MiB notebook"）的邻域。

**修复建议**：① 把 `source`/`source_preview` 纳入可截断字段（`source_truncated` 字段已存在，可直接复用并置位）；② 或给预算加"**最后手段**"：任何字段都无法再缩短时，返回一个**明确的小响应 + 错误/警告**（例如"响应超出预算，请用 `cell_indexes` 分批读"），而不是让帧越线；③ 顺带消掉"同一份文本出现两次"的重复（响应体积直接减半）；④ 用例：**5 MiB 源码 + `include_source='full'` 必须被截断或明确拒绝，且客户端存活**（现有 `v13-response-budget.test.ts` 的夹具全是大 text 输出，覆盖不到 source）。

## 三、本轮发现

修复建议：同 §2.3（把 source 纳入可截断、或加"无法再缩短即明确拒绝"的兜底、并消掉文本重复）。
设计文档对齐：D-065 的承诺①"消费者拿得到响应、会话不断"；SPEC §5.4（禁止静默截断的反面）；AGENTS §6 红线（session 不能因体积而不可用）。
