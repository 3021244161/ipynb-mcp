fix: validate what we write, in nbformat, before writing it

Found by the v4 review's E2E run with Python's own nbformat.validate — and by no
previous round, for a reason worth recording: the writer and the tests spoke the
same private dialect.

FID-1 — `cell.outputs = [...result.result.rawOutputs]` assigned the SIDECAR'S
private output shape (`outputType`, camelCase) straight into the notebook. Every
executed cell therefore turned the file into something nbformat rejects:
JupyterLab and nbconvert refuse it or lose the outputs, and this tool could not
read back what it had just written. The run reported
`write_back.performed: true` with no warning, because nothing in the codebase
disagreed with itself.

core/outputs.ts now owns both directions of the nbformat boundary: the read
direction (`rawOutputsOfCell`) had no counterpart, so `nbformatOutputsOfRaw` is
new. It is a real conversion rather than a rename because nbformat requires
`execution_count` on `execute_result` and nowhere else, so it needs the cell's
count — and both write-back paths (the normal one and the failure-path write-back
after a cancel or timeout) go through it.

FID-3 — `set_cell_type` to markdown set `execution_count = null`. nbformat
forbids the KEY on a markdown cell ("Additional properties are not allowed"),
and serializeNotebook only fills it for code cells, so the null stayed in the
user's file forever. SPEC §4.5 write rule 4 says deleted; it now deletes.

FID-4 — and the reason this cannot silently return: `selfCheckNotebook` no
longer only re-parses its own output (a parser happily reads back whatever it
wrote). It now also checks the structural rules the write paths can violate —
non-code cells carry no outputs/execution_count, output_type exists, and each
output kind has the fields nbformat requires — and aborts the write with
`selfcheck_failed` (an existing §7 code) when they do not hold. That turns
"never silently corrupts" into a statement about the RESULT rather than about
the parser, which is what R2/R9 actually promise.

FID-2 — the read direction reported "this cell has no outputs" for outputs it
could not understand, a false claim that also helped hide FID-1. Unknown kinds
now surface as `unsupported`.

FID-5 — `notebook_run_status` leaked the internal camelCase handle, so the same
field was `backup_path` from notebook_run and `backupPath` from the status tool.

The gate earned its keep immediately: it rejected three test fixtures that were
themselves invalid nbformat (none had ever been checked).

Verified: 227 unit (1 skipped), 44 integration (6 files), `pnpm smoke` 11/11.
Mutation-checked: reverting FID-1 turns the nbformat validation, the key-shape
assertion and the execution_count assertion red at once.
